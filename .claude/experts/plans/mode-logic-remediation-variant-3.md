# Доработка логики режимов Samovar — вариант 3

Дата: 2026-07-29

## Цель

Устранить все перечисленные риски логики режимов вертикальными срезами, начиная с
неподтверждённых исполнительных команд и опасных переходов состояния. Каждый срез
должен иметь явный контракт результата, поведенческий тест, проверку мутацией и
независимое code review до перехода к следующему зависимому срезу.

## Зафиксированные решения

- За один вызов `withdrawal()` разрешён максимум один переход строки.
- Ручная пауза пивного этапа `F` останавливает и нагрев, и охлаждение.
- Допустимая полоса выдержки су-вида: `уставка ± HEAT_DELTA`; текущее рекомендуемое
  значение `HEAT_DELTA` равно `1 °C`.
- Предупреждение су-вида: непрерывное отклонение больше `2 °C` в течение `60 с`.
- `SuvidHoldMinutes = 0` означает бессрочный термостат без автоматического завершения.
- Неуспешная оптимизация НБК переводит процесс в безопасное ожидание:
  подтверждённая подача `0`, нагрев выключен. Переход в `W` возможен только по
  явной команде и при ненулевых параметрах `W`.
- Lua `delay()` принимает только `0…1000 мс`.
- Физическая телеметрия и программные флаги приводов доступны Lua только для чтения.
- `APPLIED` означает подтверждение драйвером/устройством. Для GPIO это означает
  выполненную запись выхода контроллера, но не физическую обратную связь, которой
  в конфигурации нет.
- Никаких новых fallback, shim и параллельных API.

## Общий контракт исполнительных команд — X1, 9/10

### Архитектура

1. Ввести один компактный результат:
   `ACCEPTED`, `PENDING`, `APPLIED`, `FAILED`.
2. Для асинхронного регулятора хранить поколение запроса и переводить существующие
   `APPLIED/FAILED/TIMED_OUT/SUPERSEDED` safety-статусы в общий результат.
3. Не расширять `OperationStore`: это внешний HTTP-контракт, а не состояние
   исполнительного устройства.
4. Значения процесса, статистика и дедлайны меняются только после `APPLIED`.
5. Для составной команды каждый шаг подтверждается отдельно. Частичный отказ
   запускает безопасную компенсацию; если компенсация не подтверждена, состояние
   считается неизвестным/аварийным.

### Файлы

- `safety_transition.h`
- `power_regulator.h`
- `samovar_api.h`
- вертикальные потребители в `nbk.h`, `beer.h`, `valve_buzzer.h`

### Приёмка

- `PENDING` никогда не интерпретируется как успех.
- Ошибка, timeout и superseded дают `FAILED` с причиной.
- Нижний `bool` I2C не игнорируется.
- Старые несовместимые сигнатуры удалены в том же срезе.

## Волна 1. Lua — L1–L6

### L1. Запрет прямой записи режима — 10/10

- Сделать `Samovar_Mode`, `SamSetup_Mode`, `Samovar_CR_Mode` read-only в таблице
  дескрипторов Lua.
- Удалить прямой setter и его pending-owner.
- Единственный путь смены режима — существующая очередь составной транзакции
  `queue_profile_operation()` → `process_profile_operation()` →
  `switch_samovar_mode()`.
- Запись read-only значения завершает Lua-вызов явной ошибкой.

### L2. Ограничение `delay()` — 10/10

- Проверять целое значение до сужения типа.
- Разрешить `0…1000 мс`.
- Отрицательные, нецелые и большие значения завершаются `luaL_error`; `vTaskDelay`
  не вызывается.

### L3. Физическая телеметрия read-only — 9/10

- `SteamTemp`, `PipeTemp`, `WaterTemp`, `TankTemp`, `ACPTemp` сделать read-only.
- Удалить запись в `DSSensor.avgTemp`.
- Для моделирования добавить отдельные `Virtual*` только под явным
  `SAMOVAR_LUA_SIMULATION`.
- В simulation-сборке запретить все реальные actuator wrappers; управляющая логика
  реального процесса не потребляет `Virtual*`.

### L4. Флаги приводов read-only — 9/10

- `pump_started` и `valve_status` сделать read-only.
- Изменения выполняются только через `openValve`, `setPumpPwm` и подтверждённые
  аппаратные команды.
- Обновить штатные и reference Lua-скрипты, которые прямо пишут эти флаги.

### L5. Явный отказ watchdog/init — 8/10

- `lua_init()` и загрузка chunks публикуют readiness и точную причину отказа.
- Ошибка prelude/watchdog, compile или runtime не удаляется молча со стека.
- Lua-режим и Beer `L` блокируются явной ошибкой до исправления скрипта.
- Результат job: generation/ticket и состояния pending/running/succeeded/failed.

### L6. Контроль протока по реальному demand — 8/10

- Использовать общий `mode_water_flow_demanded()`.
- Не проверять проток, если клапан и охлаждающий насос выключены.
- Не подставлять фиктивные импульсы.

### Тесты Lua

- Read-only режим, датчики и флаги.
- Границы delay `-1`, `0`, `1000`, `1001`, `LONG_MAX`.
- Watchdog/init/compile/runtime failure.
- Ticket не считается выполненным до публикации terminal result.
- Simulation build не может включить реальные приводы.
- Мутации каждой read-only записи и верхней границы delay дают содержательный FAIL.

## Волна 2. НБК — N1–N5

### N1. Подтверждение команды насоса — 10/10

- `SetSpeed()` возвращает общий actuator-result.
- Сначала выполнить `set_stepper_target()`.
- Только после `APPLIED` интегрировать предыдущий подтверждённый расход,
  обновлять `nbk_P`, `time_speed`, статистику и следующий дедлайн.
- При `FAILED` выключить нагрев и перейти в явное безопасное состояние.

### N2. Убрать fallback 500 Вт / 1 л/ч — 10/10

- Удалить подстановки `500` и `1`.
- Автоматические ветви O→W без найденного optimum переводят в safe-wait.
- Safe-wait достигнут только после подтверждённой подачи `0` и выключенного нагрева.
- Если останов насоса не подтверждён, нагрев всё равно выключается, состояние остаётся
  `FAILED`, этап `W` недоступен.
- Вход в `W` — только по явной `SAMOVAR_NBK_NEXT` и с ненулевыми Power/Speed строки.

### N3. Сборка без регулятора мощности — 9/10

- Удалить ранний `return`, оставляющий zombie-session.
- Бинарный GPIO-нагрев получает `APPLIED` после записи выхода.
- Ненулевая регулируемая уставка не эмулируется и не подставляется.
- Невозможный этап завершается явной ошибкой и полным штатным cleanup.

### N4. Снимок конфигурации сессии — 8/10

- Валидировать настройки один раз при старте.
- Копировать используемые Nbk-параметры и `MainsVoltage` в `NbkSessionConfig`.
- H/S/O/W используют только snapshot.
- Изменение `SamSetup` влияет только на следующую сессию.

### N5. Две средние скорости — 4/10

- `sessionAverageRate`: подтверждённый объём / полное время сессии.
- `activeFeedAverageRate`: подтверждённый объём / время подтверждённо работающего насоса.
- Прогрев и неуспешные команды не входят в active-feed метрику.

### Тесты НБК

- I2C success/failure; PENDING→APPLIED и PENDING→FAILED регулятора.
- Snapshot двух разных конфигураций и изменение настроек во время сессии.
- Неуспешная оптимизация, подтверждённый safe-wait и запрет автоматического W.
- No-power feature matrix.
- Два расхода и два интервала для обеих средних.
- `nbk.h` остаётся CRLF-only.

## Волна 3. Пиво — BE1–BE5

### BE1. Безопасный Lua-этап `L` — 10/10

- Состояния owner: `IDLE → ENTER_QUEUED(ticket) → RUNNING(ticket) →
  EXIT_REQUESTED(nextRow) → IDLE`.
- Перед enqueue выключить нагрев, закрыть клапан, остановить охлаждающий насос и
  мешалку.
- `ProgramNum` не покидает `L`, пока job не подтверждён и затем не остановлен.
- Queue/init/compile/runtime/watchdog failure вызывает явный orderly abort.
- `beer_finish()` и mode switch используют тот же stop-handshake.

### BE2. Подтверждение мешалки — 8/10

- `set_mixer_state()` возвращает результат.
- `mixer_status` меняется только после успеха всех требуемых команд.
- Ошибки `set_stepper_by_time()` и `set_mixer_pump_target()` обрабатываются.
- Частичное включение компенсируется безопасным выключением.
- Таймер расписания не сдвигается до `APPLIED`.

### BE3. Семантическая валидация — 8/10

| Тип | Temp | Time | Устройство | Sensor |
|---|---:|---:|---|---:|
| M | цель > 0 | 0 | допустимо | 0…4 |
| P | цель > 0 | > 0 | допустимо | 0…4 |
| B | 0 | > 0 | допустимо | 0…4 |
| C | цель > 0 | 0 | допустимо | 0…4 |
| F | цель > 0 | 0 | допустимо | 0…4 |
| W | 0 | 0 | допустимо | 0…4 |
| L | 0 | 0 | `0^0^0^0` | 0 |
| A | цель > 0 | 0 | `0^0^0^0` | 0…4 |

- Маска устройств содержит только известные биты.
- При отсутствии устройства speed/on/off равны нулю.
- Для выбранного устройства on-time больше нуля, расписание непротиворечиво.
- Проверка выполняется при parse/save и повторно перед стартом.
- Ошибка line-specific, без нормализации.

### BE4. Семантика ручной паузы F — 5/10

- В начале ветки F при pause выключить heater, закрыть valve, остановить cooling pump,
  сбросить его runtime-флаг и выйти.
- Resume продолжает тот же этап без скрытого изменения прогресса.

### BE5. Сквозные переходы в L — 9/10

- Отдельные сценарии `P→L`, `B→L`, `C→L`.
- Проверять физические состояния всех исполнительных механизмов, ticket и удержание
  `ProgramNum`.
- Failed/timeout Lua-job не переводит процесс дальше.

## Волна 4. Су-вид — S1–S4

### S1. Считать только время в диапазоне — 10/10

- Состояния `HEATING`, `HOLDING`, `OUT_OF_RANGE`, `COMPLETED`.
- Полоса `setpoint ± HEAT_DELTA`.
- В полосе накапливать интервалы только между двумя последовательными наблюдениями,
  на которых состояние подтверждено как `in-band`.
- При выходе выдержка ставится на паузу.
- Отклонение >2 °C запускает таймер; после 60 с — одно предупреждение до возврата.

### S2. Собственная длительность — 9/10

- Добавить `uint16_t SuvidHoldMinutes` в профиль.
- Удалить зависимость от `program[0].Time`.
- `0` — бессрочный термостат.
- Старый профиль читается с `SuvidHoldMinutes=0`, затем мигрируется только после
  успешного decode и подтверждённой записи новой версии.

### S3. Проток только при запросе охлаждения — 9/10

- Общий demand predicate используется и счётчиком, и alarm-path.
- Без demand счётчик сбрасывается.
- Горячий су-вид без открытого охлаждения не получает ложную аварию.

### S4. Температурный предел UI — 4/10

- Добавить `SuvidHoldMinutes` в setup UI и server staging.

### Тесты су-вида

- Обе границы ±1 °C и несколько выходов/возвратов.
- 59/60/61 с отклонения >2 °C.
- Hold 0, 1 и 60 минут.

- Demand/no-demand flow matrix.

## Волна 7. БК — BK1–BK3

### BK1. Причина подтверждения кипения — 4/10

- Зафиксировать первую фактическую причину в момент подтверждения:
  `STEAM`, `PIPE`, `TANK_AND_WATER`, `TANK`, `WATER`. `PIPE` — явно

### BK3. Индикация точности — 4/10

- `STEAM` и `PIPE` — более точные сигналы.

## Общий demand-gate протока

`mode_water_flow_demanded()` возвращает true только если одновременно:

- `UseWS` включён;
- открыт клапан либо реально активен охлаждающий насос.

Состояние нагрева в predicate не входит: охлаждение может оставаться запрошенным при
выключенном нагревателе, и потеря протока в этот момент всё равно является аварией.

Этот predicate:

1. управляет накоплением `WFAlarmCount`;
2. повторно проверяется непосредственно перед `request_emergency_stop()`;
3. используется одинаково во всех режимах;
4. заменяет `water_pulse_count_set(100)` в beer alarm-path.

## Проверки

Для каждого task ID:

1. тест требуемого поведения;
2. минимум два разных значения/источника;
3. извлечение реального production-кода;
4. проверка мутацией и содержательный текст FAIL;
5. targeted smoke;
6. независимый terra-review;
7. исправление замечаний и повторный review.

После всех срезов:

1. `python3 tools/build_web_assets.py`;
2. `python3 tools/smoke_data_raw_build.py`;
3. browser-проверки через `playwright-cli`;
4. `python3 tools/run_smoke_tests.py`;
5. последовательно `pio run -e` для всех окружений из `platformio.ini`;

7. финальный `/goal` reviewer-loop до ответа без ошибок и предупреждений.

Smoke-тесты и PlatformIO не запускаются одновременно.

## Риски и защита

- `nbk.h` сохраняется CRLF-only.
- Новая версия профиля не изменяет V1 decode и не очищает mixed namespace.
- Telemetry snapshot остаётся в установленном stack budget.
- Ошибки hardware apply не превращаются в UI-успех.
- Смена режима и Lua stop не обходят существующий barrier.
- `data/` не редактируется вручную; источник — `data_raw/`.
- Codebase map обновляется для каждого реально затронутого node.
