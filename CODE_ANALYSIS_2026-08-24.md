# Анализ кода Samovar — 24.08.2026

База: коммит `6466f602`, рабочее дерево чистое. **Только анализ, правок не вносилось.**
Метод: 7 параллельных сабагентов (архитектура/конкурентность, C++/память, логика перегонных
режимов, логика пиво/сувид/Lua/детектор, веб-API/хранение, UI/UX, железо), затем личная
верификация ключевых находок по коду. Помечено: ✔ — проверено лично цитатой кода/расчётом,
◻ — цитата агента, лично не перепроверялось.

## Уровень 1. Блокеры

### 1. ✔ Страница настроек не сохраняется на заводских значениях — `data_raw/setup.htm:172,484`
Сервер подставляет в поле значение, умноженное на 100 (`WebServer.ino:1503`:
`return (String)(SamSetup.StepperStepMl * 100);`), заводское значение `STEPPER_STEP_ML 1020`
(`Samovar_pin.h:249`) → в поле попадает `102000`. Валидатор страницы
(`{ name: 'StepperStepMl', integer: true, min: 0, max: 65535 }`) режет по 65535, а
`submitSetupForm` (`setup.htm:200`) прерывает отправку **всей** формы:
`if (!SamovarApp.validateNumericFields(form, setupNumericSchema)) return false;`.
Итог: ни один параметр на странице сохранить нельзя, сообщение — «Поле «StepperStepMl»:
максимум 65535». Если пользователь «исправит» число на 1020, форма отправит его как
шаги-на-1-мл (`WebServer.ino:1983`, диапазон 0..65535) — то есть подставит верное значение
случайно. То же для `StepperStepMlI2C` (дефолт 16000 → 1600000).
Рядом `calibrate.htm` сделан правильно: подпись «Шагов на 100 мл» и деление на 100 перед
отправкой (`calibrate.htm:140,193`).
Тестами не ловится: `tools/test_numeric_input_ui_browser.py` подставляет `"StepperStepMl": "100"`.

### 2. ✔ Главный цикл замирает на ~2 секунды каждые 4 минуты — `Menu.ino:719-723`
`CurMin = (millis() / 1000);` при `uint8_t CurMin` (`Samovar.h:295`) — счётчик заворачивается
каждые 256 с, поэтому `if (CurMin == 120) menu_reset_lcd();` срабатывает не «один раз через
2 минуты», а бесконечно, раз в 4 мин 16 с. Внутри — `lcd.begin(20,4); lcd.init();`
(`Menu.ino:220-221`), каждый вызов содержит `delay(50) + delay(1000)`
(`libraries/LiquidCrystal_I2C_ESP32/LiquidCrystal_I2C.cpp:96,100`) → ~2.1 с блокирующей
задержки прямо в `loop()`, всё это время удерживается `xI2CSemaphore`.
Последствия: на 2 с встают обработка аварийной кнопки в `loop()`, `tick_self_test()`,
`mode_dispatch_loop()`; `SysTicker` не может взять шину I2C (таймаут 1000 мс,
`I2CStepper.h:171`) и помечает насос/мешалку отсутствующими. Плюс `lcd.init()` дёргает
`Wire.begin()` — переинициализация драйвера I2C на ходу. Экран при этом моргает круглосуточно.
Ни один smoke-тест не покрывает (`menu_reset_lcd`/`CurMin` — 0 совпадений в `tools/smoke_*.py`).

### 3. ✔ Аварийный останов не сбрасывает состояние процесса — `alarm.h:88-121`
`perform_emergency_stop()` гасит железо (`set_power(false)`, `open_valve(false,true)`,
`stopService()`, `set_stepper_target(0,0,0)`), но не трогает ни `SamovarStatusInt`, ни
`startval`, ни `PauseOn`/`program_Wait`. Полный сброс живёт только в `reset_sensor_counter()`
(`sensorinit.h:564-567`), которую аварийный тракт для не-НБК режимов не вызывает.
Следствия, проверенные по коду:
- **Отбор может перезапуститься сам.** `withdrawal()` (`logic.h:100-112`) гейтится только по
  `SamovarStatusInt` (WITHDRAWAL/AUTOPAUSE/PAUSED) — ни `PowerOn`, ни `alarm_event` там нет.
  Ветка возобновления автопаузы (`logic.h:210-215`) при остывании колонны делает
  `pause_withdrawal(false)` → `startService()` (`logic.h:298-303`), тоже без проверки `PowerOn`.
  Итог: после аварии нагрев снят, вода охлаждения закрыта (осознанное решение П67), колонна
  остывает — и насос отбора снова начинает качать через горячую неохлаждаемую колонну.
- **Мешалка остаётся включённой.** `RELE_CHANNEL2` пишется только в `beer.h:964-1017`, а обе
  функции, которые могли бы её снять (`beer_stage_tick`, `check_mixer_state`), начинаются с
  `if (heater_safety_latched()) return;` (`beer.h:617`, `beer.h:892`). После аварии во время
  варки мешалка крутится в горячем сусле до перезагрузки или смены режима.
- ◻ **Залипает `beerCoolingPumpActive`** (`beer.h:66`): `set_pump_pwm(0)` в `alarm.h:117` флаг
  не сбрасывает → `mode_water_flow_demanded()` продолжает требовать воду → каждую секунду
  новая авария «нет протока» + `set_buzzer(true)`, который обнуляет счётчик писков
  (`valve_buzzer.h:65`) → зуммер не замолкает никогда, журнал забит спамом.

### 4. ✔ Обновление веб-интерфейса физически не помещается в файловую систему — `WebServer.ino:3001-3022`
Схема stage/commit кладёт все 21 файл во временные `*.tmp` и лишь потом переименовывает, то
есть в пик на разделе живут два комплекта. Расчёт по факту:

| | сырые байты | с блоками LittleFS 4 КБ |
|---|---|---|
| весь `data/` | 382 641 | 520 192 |
| набор для скачивания (21 файл) | 365 456 | 421 888 |
| **пик** | 748 097 | **942 080** |
| раздел `spiffs` (`partitions.csv`, 0xC0000) | | **786 432** |

Дефицит ~152 КБ; даже без блочного округления запас всего ~38 КБ, а на том же разделе лежит
журнал перегонки `data.csv`/`data_old.csv`. Отказ штатный (откат, маркер версии не пишется),
но пользователю не показывается — только `Serial.println`, и повторяется при каждой загрузке.
Тест `tools/smoke_web_interface_update.py` пинит порядок stage→commit→маркер, свободное место
не проверяет.

## Уровень 2. Высокий приоритет

### 5. ✔ `load_lua_script()` вешает `loop()` до 20 секунд — `lua.h:1951`
`bool lua_locked = lua_state_lock(portMAX_DELAY);` — ожидание без таймаута, а вызывается
функция из главного цикла (`Samovar.ino:2856`) и из коммита профиля (`Samovar.ino:449`).
Задача `do_lua_script` держит тот же `xLuaSemaphore` весь прогон чанка
(`lua.h:2010` `sr = lua_exec_locked(local_job_script);`, потолок `LUA_CHUNK_TIMEOUT_MS 20000`),
и так для двух скриптов подряд. Сохранение скрипта из веба во время отбора → замирает отбор,
шаговик, энкодер, зуммер, `mode_dispatch_loop()`.

### 6. ✔ Ошибка в личном `script.lua` обрывает варку пива — `lua.h:2071-2124`, `beer.h:698`
Флаг `periodicFailed` — один на оба скрипта: взводится и на ошибке общего `script.lua`
(`lua.h:2083`), и на ошибке режимного (`lua.h:2108`), после чего целиком уходит в пивной job
(`lua.h:2124` → `lua.h:514-517`). `beer_stage_tick()` на строке 'L' видит не-SUCCEEDED и делает
`beer_abort_config_error("Ошибка Lua: job завершился без подтверждённого запуска")` → варка
завершается, нагрев снят, сусло брошено. Это прямо противоречит комментарию `lua.h:305-312`
(«script1 не глушит планировщик»). Тест `tools/smoke_lua_periodic_failure_stop.py:226`
подменяет `finish_beer_lua_periodic_result` заглушкой и этого не ловит.

### 7. ✔ `BKPower` можно сохранить ниже порога включения — `WebServer.ino:2004`, `BK.h:100-108`
`{"BKPower", &SetupEEPROM::BKPower, 0.0f, 10000.0f}` — нижняя граница 0, тогда как для
соседнего `DistTemp` её специально подняли до 30 именно от этого класса ошибок
(`WebServer.ino:2011`). Порог рабочего режима регулятора — 40 В (KVIC/RMVK) или 100 Вт (SEM)
(`power_regulator.h:46-48`); уставка ниже уводит регулятор в SLEEP и обнуляет
`target_power_volt` (`power_regulator.h:811-816`) молча. Ветка `BK.h:100` одноразовая
(`current_power_mode_is(POWER_SPEED_MODE)`), второй раз не сработает. Куб остывает, авария не
взводится — `check_power_error()` в SLEEP не смотрит (`power_regulator.h:696-733`).

### 8. ✔ Три импульса в секунду навсегда отключают защиту «нет воды» — `Samovar.ino:885-893`
```
if (waterPulses < 3) waterPulses = 0;
...
if (mode_water_flow_demanded() && waterPulses == 0) WFAlarmCount++; else WFAlarmCount = 0;
```
Антидребезг работает наоборот: 3 и более импульсов за цикл обнуляют счётчик аварии. Датчик
сидит на GPIO36 (`Samovar_pin.h:206`) — вход-только, без внутренней подтяжки, с известной
кремниевой ошибкой ложных импульсов. Наводка от силового кабеля ТЭНа на длинном проводе даёт
эти 3 импульса, дефлегматор при этом сухой.

### 9. ✔ Blynk V17 = 0 не останавливает насос — `Blynk.ino:203-204`
`stepSpeed = (uint16_t)get_speed_from_rate(0)`, а `get_speed_from_rate` зажимает снизу
(`logic.h:59` `if (v < 1) return 1;`); `set_pump_speed` отбрасывает только строго меньшее
(`logic.h:344` `if (pumpspeed < 1) return;`). Значит 1 проходит, `CurrrentStepperSpeed = 1`,
`startService()`. Комментарий выше («Ноль снова останавливает насос») описывает поведение,
которого нет. Оператор шлёт 0, чтобы прекратить отбор — насос продолжает ползти.

### 10. ✔ График: живая линия «Строка программы» всегда пустая — `data_raw/chart.js:83`
`ajaxToRow` читает `data.ProgNum`, а `/ajax` отдаёт поле под именем `ProgramNum`
(`Samovar.ino:3561`); имени `ProgNum` в `/ajax` нет вовсе (проверено). В CSV колонка
действительно `ProgNum` (`WebServer.ino:997`), поэтому историческая часть графика рисуется, а
всё, что дорисовывается в реальном времени, — обрывается на «сейчас».

### 11. ✔ Детектор: сброс коэффициента не возвращает насосу скорость — `impurity_detector.h:558-561`
`correctionFactor` применяется разово, через `apply_detector_speed_correction()`
(`impurity_detector.h:543-549`). Ветки выключения детектора ставят `correctionFactor = 1.0f`
и делают `return`, не применяя новое значение. Пользователь выключил детектор в настройках —
в интерфейсе коррекции больше нет, а насос как шёл на 70 % от заданного, так и идёт.

### 12. ◻ Чтение одного байта по I2C не отличает ноль от отказа шины — `I2CStepper.h:170-175`
`value = I2C2.readByte(...); ... return true;` — библиотека
(`libraries/iarduino_I2C_connect/src/iarduino_I2C_connect.cpp:42-49`) игнорирует
`endTransmission` и возвращает 0 при любом отказе. Так читаются `status`, `error`, `relayMask`,
`sensorFlags`, `ackSeq`. Соседний `i2c_stepper_read_block` (`I2CStepper.h:177-196`) ошибки
проверяет — контракт разъехался. Помеха в середине пачки → «ошибок нет, реле выключены»,
прошивка верит и перезаписывает `relayMask` нулём.

### 13. ◻ Кнопка нагрева в вебе — переключатель, решение принимается по устаревшему кэшу — `index.htm:691`
`onclick='if (HeaterPowerOn && !confirm("Выключить нагрев?")) ...; sendCommand("power=1")'`, а
прошивка трактует `power` как переключатель от **своего** состояния (`WebServer.ino:2431-2432`).
`HeaterPowerOn` обновляется только телеметрией, и в список «протухших» показаний
(`index.htm:545 staleReadingIds`) состояние нагрева не входит. Пока связь моргает, кнопка
показывает старую подпись: если нагрев за это время включили с энкодера/из Lua, тап **выключит**
его без подтверждения. Плюс `sendCommand` (`app.js:863`) не блокирует кнопку и не имеет
таймаута (`AbortController` есть у `fetchJson`/`pollAjax`, но не здесь) — двойное нажатие даёт
два переключения, то есть нагрев вернётся.

### 14. ◻ Аварийный останов может не остановить дозирующий насос по I2C — `alarm.h:118`
`set_stepper_target(0, 0, 0)` — возврат отброшен; путь `requireI2c = false`
(`samovar_api.h:328`) молча выходит, если `i2c_stepper_config_begin()` занят
(`I2CStepper.h:399`), а его держит секундный `refresh_i2c_stepper_cache()` из `SysTicker`
(`Samovar.ino:1659-1660`). Окно ~15–30 мс дважды в секунду.

### 15. ◻ Аварийная кнопка на GPIO35 с несуществующей подтяжкой — `Samovar.ino:1449-1451`
`pinMode(ALARM_BTN_PIN /*35*/, INPUT_PULLUP)` — на GPIO34–39 подтягивающих резисторов нет
физически, вызов молча ничего не делает, а логика построена на FALLING и `== LOW` при старте.
Без внешнего резистора вход висит в воздухе: ложный аварийный останов от наводки либо уход в
аварию сразу после загрузки. Аналогично энкодер на LILYGO (35/39/36, `Samovar_pin.h:94-96`) и
безусловно включённая кнопка меню на S3 (GPIO47, `Samovar_pin.h:60`, `LOW_PULL` без внешнего
резистора → самопроизвольное `set_power(true)`).

### 16. ◻ Барьер смены режима: надзор выключается раньше, чем снят нагрев — `WebServer.ino:200`, `mode_registry.h:258-262`
`queue_profile_operation()` из задачи async_tcp ставит `mode_switch_barrier_active = true`, не
выключая реле; с этого момента `mode_dispatch_alarm()` уходит в ранний return (перегрев, проток
воды, отказ датчиков, `check_power_error()` — всё выключено). Фактическое снятие нагрева идёт
позже, в `loop()`. Комментарий в `mode_registry.h:259-261` описывает обратный порядок. Смена
режима без поля `WProgram` принимается при работающем нагреве (`WebServer.ino:2276`).

### 17. ◻ Аварийный надзор — последний в секундном такте, после I2C и записи в флеш — `Samovar.ino:1659-1679`
Порядок: датчики → два `refresh_i2c_stepper_cache` (каждый ждёт мьютекс I2C до 1000 мс) →
журнал → снимок → `append_data()` → и только потом `mode_dispatch_alarm()`. При подвисшей шине
такт растягивается до 2–4 с; сторож живучести (порог 10 с) это пропускает.

### 18. ◻ Настройки и таблица программы копируются между ядрами без блокировки
`Samovar.ino:402` (`SamSetup = active_profile_operation.settings;`, loop) против
`WebServer.ino:2183` (`SetupEEPROM staged = SamSetup;`, async_tcp) — 536 байт без лока;
`program_io.h:144-156` (`program_commit`) против `serialize_program_for_mode()`
(`WebServer.ino:1160,1451,2700`). Два быстрых сохранения подряд или сохранение во время
открытой второй вкладки → в NVS уезжает смесь старых и новых полей; readback-verify этого не
ловит, он сверяет записанное с записанным.

## Уровень 3. Средний приоритет (сводно)

**Логика перегонки**
- Лестницы снижения мощности не имеют дна и обратного хода: `reduce_power_by_volts`
  (`runtime_helpers.h:324-325`), захлёб (`alarm.h:191`), предаварии по воде (`alarm.h:302-320`).
  Провалившись ниже порога, уставка обнуляется, а восстановление `+0.5 * PWR_FACTOR`
  (`alarm.h:233`) от нуля порога уже не достигает; в SEM-варианте восстановление
  мультипликативное — от нуля это ноль навсегда.
- `Power` в строке программы: значение ≤ 40 (для SEM ≤ 400) трактуется как **дельта**, выше —
  как абсолют (`power_regulator.h:851,859-863`). Валидации нет
  (`validate_rect_program_startable`, `logic.h:736-750`, поле `Power` не смотрит), в интерфейсе
  это не подписано. Пользователь SEM вводит «250 Вт» → колонна получает «текущая + 250».
- `Power = 0` в первой строке: переход разгон→стабилизация не меняет мощность вовсе
  (`alarm.h:350`) — колонна стабилизируется на разгонном максимуме. **Поведение закреплено**
  `tools/smoke_program_power_row.py` и `smoke_alarm_rect_stabilize_power.py`; правильный выход —
  не давать сохранить такую программу, а не менять диспетчер.
- Дистилляция: бустерный ТЭН выключается только в `distiller.h:278` при
  `program[num-1].Power != 0` — программа со всеми `Power = 0` оставляет буст включённым на весь
  перегон.
- `column_wetting()` (`logic.h:1290-1294`) не возвращает мощность после успешного смачивания —
  дальше вся ректификация идёт на 80 % от задуманного.
- БК и дистилляция: нет отсечки по перегреву пара/царги (`mode_common.h:71-82` смотрит только
  `WaterSensor`/`ACPSensor`).
- `check_boiling()` требует открытого клапана охлаждения (`logic.h:1105`) — на аппарате с ручным
  вентилем детект кипения не сработает никогда.
- НБК: устаревший флаг `nbk_overflow_happened` глушит первую коррекцию после реального захлёба в
  строке 'W' (`nbk.h:906`); `commitProgram` (`nbk.h:443-455`) сбрасывает соседние флаги, но не его.
- НБК: храповики снижения M и P не имеют дна и обратного хода (`nbk.h:573-594`, `nbk.h:907-913`).
- RMVK: старт нагрева всегда идёт через `MAX_VOLTAGE (230)`; ответ «OFF» на команду включения
  считается успехом; телеметрия перетирает `target_power_volt` фактом, из-за чего рассогласование
  «заказано/фактически» становится ненаблюдаемым.

**Пиво / сувид / Lua**
- Ручная пауза на строках 'L' и 'W' рапортует «поставлено на паузу», но ничего не гейтит
  (`logic.h:317-318` против `beer.h:641-642`). Негейтуемость 'L'/'A' сама по себе — осознанное
  решение (`tools/smoke_beer_manual_pause_gates_all_outputs.py:154`), чинить надо сообщение.
- На строках 'M'/'P'/'B'/'L'/'A' нет надзора за перегревом вообще: `beer_check_cooling_limits()`
  выходит на первой строке для всех типов кроме 'C'/'F' (`beer.h:554`), а Lua может поднять реле
  нагрева сырой записью в пин (`lua.h:1043`).
- Сувид: полоса зачёта выдержки совпадает с полосой самого термостата (`suvid.h:115-126`,
  HEAT_DELTA 1 °C) — релейный термостат всегда перелетает границы, и выдержка идёт медленнее
  реального времени. Любой сброс питания молча обнуляет накопленное (`suvid.h:110`), в снимок
  `/state.csv` выдержка не пишется.
- `http_request` из Lua блокирует до 4 с на вызов, удерживая `xLuaSemaphore`; хук проверяет
  дедлайн раз в 1000 инструкций (`lua.h:34,1541`).
- `setTimer(n, x)`: `uint16_t b = luaL_checknumber(...)` (`lua.h:1476`) — отрицательное/NaN даёт
  неопределённое поведение, 100000 тихо превращается в 34464.
- `acceleration_temp == 60 * 6` (`alarm.h:373`) — точное сравнение на счётчике, который Lua может
  записать (`lua.h:746-747`, RW 0..65535); скрипт выставил 400 → колонна навсегда в стабилизации.

**Веб / хранение / ФС**
- Частичная установка интерфейса без отката и без прерывания цикла (`WebServer.ino:3025-3031`) —
  новая `index.htm` со старым `app.js.gz`.
- При реально заполненной ФС уборка и тревога недостижимы: ранний возврат `FS.ino:577-581` стоит
  до блока освобождения места (`FS.ino:616`) и до `SendMsg("Заканчивается память!")`
  (`FS.ino:631`). Частичная запись считается успешной.
- `/state.csv` пишется не атомарно (`FS.ino:410-437`): `FILE_WRITE` усекает файл сразу, успех
  проверяется как `println(...) > 0`. Обрыв питания во время записи → при загрузке успешно
  разбирается укороченная программа, пользователь видит «восстановлено».
- `/lua?script=` принимает любое имя файла (`WebServer.ino:1059`, `lua.h:1893-1896`):
  `/lua?script=data.csv` → `readString()` тянет весь журнал одним куском в `loop()`.
- Цвета датчиков — единственные строковые поля, которые молча усекаются
  (`WebServer.ino:2225-2227`), остальные отвечают 400.
- Сырой EEPROM при миграции принимается без валидации строк и float (`NVS_Manager.ino:647,660`).
- `Descr` : `maxlength='250'` в браузере считает символы, `String::length()` — байты
  (`WebServer.ino:2689`); для кириллицы реальный предел ~125 символов, ответ 400 без объяснения.
- `/i2cpump` резервирует ячейку OperationStore и выбрасывает её номер (`WebServer.ino:786-797`) —
  8 ячеек, активная работа с насосом вытесняет результаты сохранений настроек.
- Скачивание журнала не синхронизировано с дозаписью (`WebServer.ino:2836-2847`).

**Архитектура/конкурентность**
- Сторож просроченных операций переводит запись в FAILED, но не снимает флаг-владелец
  (`operation_store.h:245-276`) → канал I2C-команд заклинивает до перезагрузки; второй тупик там
  же при несовпадении id (`Samovar.ino:1252-1268`).
- Барьер смены режима не снимается на пути отказа (`Samovar.ino:520-523`) → `loop()` вечно уходит
  в ранний return.
- `loop()` не покрыт ни одним сторожем: `esp_task_wdt` не взводится ни на одну задачу,
  живучесть SysTicker наблюдается **из** `loop()` (`Samovar.ino:2679-2701`).
- Задача аварийной кнопки — приоритет 3 на ядре 1, где async_tcp работает с приоритетом 5.
- Сувид управляет нагревателем прямо из задачи надзора, с `vTaskDelay(50)` внутри
  (`suvid.h:118` → `beer.h:1165`).
- `set_current_power_mode_value()` молча теряет запись при занятом локе (`runtime_helpers.h:317-322`).

**Железо**
- 16-битные регистры I2C пишутся двумя транзакциями (`I2CStepper.h:212-217`) — между ними
  устройство видит смешанное значение, отката нет.
- Локальный запасной путь шаговика игнорирует направление (`I2CStepper.h:389`): при отвале платы
  расширения `set_stepper_target(speed, 1, steps)` качает в обратную сторону и возвращает `true`.
- `tools/check_stepper_isr_iram.py` даёт ложное «ок» в трёх случаях: обход не рекурсивный,
  косвенные `callx*` не ловятся регуляркой (`:119`), и сам факт регистрации с
  `ESP_INTR_FLAG_IRAM` не проверяется (в ветке core 3.x флага нет).
- 500 мс до безопасного выключения выходов (`Samovar.ino:2383-2385`): мешалка на GPIO15
  (strapping, аппаратная подтяжка вверх при сбросе) гарантированно включена первые полсекунды
  каждой загрузки на платах с активным высоким уровнем.
- Blynk дёргают из двух задач без синхронизации (`Samovar.ino:1491,1541` против `:2729-2730`).
- 85 °C — заводское содержимое scratchpad DS18B20 после сброса питания — принимается как валидная
  температура (`sensorinit.h:281` отсекает только `< -10`), усреднения в поле `avgTemp` нет.

## Архитектурные наблюдения

- **Монолиты по необходимости.** `Samovar.ino` 3955 строк, `WebServer.ino` 3272, `Samovar.h` ~239
  определений глобалов (58 `volatile`) — следствие модели Arduino (все `.ino` склеиваются в одну
  единицу трансляции), а не небрежности. Дробить дальше можно только партиалами.
- **Слоевое смешение «режим ↔ веб».** Автомат смены режима (`switch_samovar_mode`), остановка
  приводов и барьер живут в `WebServer.ino:1587-1828` — это ядро логики режимов, а не веб.
- **Состояние операции размазано по трём местам** (флаг `pending_*`, буфер команды, запись в
  `operationStore`) — отсюда оба тупика канала I2C-команд.
- **Два источника правды в диспетчеризации**: `mode_dispatch_alarm()` выбирает по `Samovar_Mode`,
  `mode_dispatch_loop()` — по `SamovarStatusInt`. Асимметрия осознанная и запинена тестами.
- **`heater_state` — флаг без владельца**: 8 точек записи в трёх файлах из двух задач; гонки нет
  только благодаря порядку вызовов.
- **`reset_sensor_counter()` — единственная точка полного сброса**, сцеплена с побочными
  действиями (закрытие лога, чтение барометра, сброс Lua-статуса). Похоже, именно поэтому её не
  зовут из аварийного тракта — и отсюда блокер №3.
- **Проверка порядка локов ограничена одним уровнем вызова** (`tools/smoke_lock_order.py:20-26`) —
  новая цепочка глубиной 2+ появится молча.
- **Мёртвые подсистемы**: `USE_WATER_VALVE`, `USE_CRASH_HANDLER` (~185 строк), 
  `USE_STEPPER_ACCELERATION`, `COLUMN_WETTING`, `GetBMPTask` — не включены ни в одном из семи
  окружений. `Samovar_CR_Mode` — дубликат `Samovar_Mode`, но торчит в контракте Lua-переменных.
- **`tools/smoke_offline_boot_stability.py:64` сторожит существование `http_sync_request_post()`**
  (`WebServer.ino:3229`), у которой нет ни одного вызова.
- Устаревший комментарий `libraries/Async_TCP/src/AsyncTCP.h:56` («ядро 0») противоречит
  `platformio.ini:52` (`CONFIG_ASYNC_TCP_RUNNING_CORE=1`) — ломает любой анализ гонок.

## Чем бы занялся в первую очередь

1. №1 (настройки не сохраняются) — правка на одну строку в `setup.htm`, эффект максимальный.
2. №2 (`CurMin`) — одна строка, снимает 2-секундные замирания цикла и износ I2C.
3. №3 (сброс состояния при аварии) — требует решения владельца: развязать «сброс состояния» и
   «сброс периферии» в `reset_sensor_counter()`, либо добавить гейт `alarm_event`/`PowerOn` в
   `withdrawal()` и снятие мешалки в `perform_emergency_stop()`.
4. №4 (место на SPIFFS) — считать свободное место перед staging и отказывать заранее с внятным
   сообщением; иначе механизм обновления мёртв.
5. №6, №7, №9, №10, №11 — локальные правки с понятным сценарием отказа.
