# Переход рабочих страниц на статический gzip и AJAX-инициализацию

## Цель

Перевести все страницы интерфейса, кроме `setup.htm`, с серверной подстановки
`%ПЛЕЙСХОЛДЕРОВ%` на готовые gzip-файлы. Начальные данные страницы получать одним
запросом `GET /ui-bootstrap`. Сохранить существующие контракты `/save`, `/program`,
`/ajax`, очередь операций и проверку активного режима.

## Границы

В работе:

- `index.htm`, `beer.htm`, `cheese.htm`, `distiller.htm`, `bk.htm`, `nbk.htm`;
- `chart.htm`, `program.htm`, `calibrate.htm`, `calibrate_ph.htm`;
- общий загрузчик начальных данных в `app.js`;
- новый read-only маршрут `/ui-bootstrap`;
- сборка `data/`, список веб-обновления, тесты и документация.

Не входит в работу:

- `setup.htm` и `setupKeyProcessor()`;
- изменение формата профиля или NVS;
- изменение `/save`, `/program` или регулярно опрашиваемого `/ajax`;
- редизайн страниц;
- новые режимы, fallback или параллельный старый способ загрузки данных;
- динамическое gzip-сжатие на ESP32.

## Зафиксированная архитектура

1. HTML хранится в `data_raw/` в читаемом виде, а в `data/` попадает только как
   детерминированный `.gz`.
2. При открытии страницы браузер один раз запрашивает `/ui-bootstrap`.
3. Сервер возвращает один плоский JSON с типизированными значениями: числа остаются
   числами, признаки — `true/false`, текст — JSON-строками. HTML-фрагменты вроде
   `checked`, `selected` и `display:none` сервер не формирует.
4. Страница сначала применяет bootstrap-данные, затем запускает штатный опрос
   телеметрии. Это исключает гонку первого отображения.
5. При ошибке bootstrap страница показывает явную ошибку и не разрешает команды,
   зависящие от начальных данных. Повторного скрытого пути через плейсхолдеры нет.
6. `/ui-bootstrap` не принимает параметры, отвечает с `Cache-Control: no-store` и
   отклоняет запросы с любыми параметрами как `400 BAD_REQUEST`.
7. Во время активного барьера переключения режима endpoint отвечает `503`: нельзя
   возвращать режим из одного состояния и программу из другого. В остальных случаях
   `SamSetup` копируется под `configMux`, а программа сериализуется существующим
   `serialize_program_for_mode()`, который сам делает согласованный снимок.
8. Описание и список Lua-кнопок копируются через существующие runtime-state helpers с
   таймаутом `0`. Если lock занят, endpoint сразу отвечает `503`, не ожидая в
   `async_tcp`.
9. Ответ формируется через `AsyncResponseStream`, поле за полем. Большой временный
   `String` со всем JSON не создаётся.
10. Ошибки снимка обнаруживаются до создания stream и дают честный `503`. После начала
    потокового ответа нехватку памяти нельзя подменить другим HTTP-статусом; результат
    `json_write_escaped()` проверяется, а оборванный JSON считается явной ошибкой на
    клиенте.

## Контракт `/ui-bootstrap`

Ответ содержит только данные, уже показываемые рабочими страницами:

- `mode`, `version`, `powerUnit`;
- `program`, `description`, `luaButtonList`;
- `steamColor`, `pipeColor`, `waterColor`, `tankColor`, `acpColor`;
- `steamVisible`, `pipeVisible`, `waterVisible`, `tankVisible`,
  `pressureVisible`, `programNumberVisible`;
- `i2cStepperVisible`, `i2cPumpVisible`;
- `beerBrewOrder`, `pwmLow`, `pwmValue`, `nbkDp`;
- `columnDiameter`, `columnHeight`, `packDensity`, `heaterResistance`,
  `mainsVoltage`, `heaterMaxPower`;
- `stepperMaxSpeed`, `stepperStepsPerMl`, `i2cStepperStepsPerMl`;
- `calibrationRunning`, `calibrationPump`;
- `cheesePhSlope`, `cheesePhOffset`, `cheesePhSmoothPercent`.

Токены, пароли, Wi-Fi, Telegram, MQTT и Blynk в ответ не входят.

## Задача 1. Серверный контракт и его тесты

### Сначала тесты

Добавить source-derived smoke-тест, который извлекает реальный обработчик и проверяет:

- маршрут зарегистрирован ровно один раз как `GET`;
- параметры запрещены;
- `Cache-Control: no-store` присутствует;
- `configMux` защищает копирование `SamSetup`, но не удерживается во время JSON-записи;
- используются существующие снимки программы, описания и Lua-списка без ожидания lock;
- активный барьер переключения режима даёт `503` до снимка программы;
- строки корректно экранируются через общий JSON helper;
- два разных режима возвращают две разные программы и аппаратные признаки;
- ошибка копирования runtime-данных даёт `503`, а не частичный JSON;
- мутации удаления блокировки, экранирования, проверки параметров и `503` падают по
  содержательным assert-ам.

### Реализация

- В `WebServer.ino` добавить небольшой `UiBootstrapSnapshot` и функции захвата и
  потоковой записи ответа.
- Минимально расширить `copy_lua_button_list_cache()` параметром timeout, сохранив
  прежнее значение по умолчанию; новый endpoint передаёт `0`.
- Не выполнять NVS, I2C, OneWire, SPIFFS-запись или ожидания в обработчике.
- Зарегистрировать `/ui-bootstrap` рядом с `/ajax`.
- Не менять `send_ajax_json()`.

### Готово, когда

- целевой smoke-тест проходит со всеми мутациями;
- существующие route/profile/runtime smoke-тесты проходят;
- ревью C++ не находит гонок, блокирующей работы и лишних аллокаций.

## Задача 2. Общий frontend-загрузчик и пилот `cheese.htm`

### Сначала тесты

Расширить браузерный тест сыра и добавить статические проверки:

- bootstrap запрашивается один раз и раньше первого `/ajax`;
- программа, описание и Lua-кнопки приходят из JSON;
- ошибка `400/503`, обрыв и битый JSON показаны пользователю;
- команды до успешной загрузки недоступны;
- в `cheese.htm` не осталось плейсхолдеров;
- обычный символ `%` не повреждает страницу.

### Реализация

- В `app.js` добавить единственный общий `loadUiBootstrap()` и простой механизм
  передачи данных в callback страницы.
- Не создавать отдельный framework, event bus или хранилище состояния.
- В `cheese.htm` убрать `%WProgram%`, `%Descr%`, `%btn_list%` и заполнить их после
  bootstrap.
- После удаления шаблонизатора вернуть `%%` к обычным `%`, где они были нужны только
  для экранирования ESPAsyncWebServer.

### Готово, когда

- сыр полностью работает на desktop/mobile и в светлой/тёмной теме;
- прямой переход в настройки, программа, история, Lua и устройство не сломаны;
- ревью frontend-кода не находит fallback, дублирования и скрытых ошибок.

## Задача 3. Основные страницы режимов

Эту задачу можно выполнять двумя параллельными ветвями после задачи 2:

### 3A

- `index.htm`;
- `beer.htm`.

### 3B

- `distiller.htm`;
- `bk.htm`;
- `nbk.htm`.

Для каждой страницы:

1. Сначала добавить браузерные сценарии с двумя разными bootstrap-ответами и общий
   fixture `/ui-bootstrap` для остальных существующих браузерных тестов.
2. Удалить все `%...%`.
3. Заполнить программу, описание, Lua-кнопки, цвета, PWM, NBK и I2C-признаки из
   типизированного JSON.
4. Запускать telemetry только после успешной инициализации.
5. Проверить ошибку bootstrap, старый/пустой набор данных, мобильную ширину и отсутствие
   console/page errors.
6. Не менять логику сохранения программы и управления процессом.

Каждая параллельная ветвь проходит отдельное ревью до объединённой проверки.

## Задача 4. Служебные страницы

Для каждой страницы сначала написать тест успешной загрузки и явной ошибки. Проверить

операционные waiter-ы калибровки и сохранения профиля.

## Задача 5. Gzip, маршруты, обновление и документация

### Сборка assets

- Добавить десять переведённых HTML-файлов в `COMPRESS`.
- Оставить `setup.htm` несжатым.
- Усилить build smoke: в `data/` для переведённых страниц есть только `.htm.gz`, а
  сырой `.htm` отсутствует.
- Добавить общую проверку после разворачивания include: плейсхолдеры разрешены только в
  `setup.htm`. Проверка обязана видеть имена с точкой (`%ColDiam_1.5%`), которые текущая
  регулярка сборщика пропускает; случайный одиночный `%` плейсхолдером не считается.

### WebServer

- Переведённые страницы отдавать статически, без template callback.
- Сохранить проверку активного режима для прямых URL режимов.
- Удалить `indexKeyProcessor()`, `indexKeyProcessorWithSnapshots()`,
  `calibrateKeyProcessor()` и ставшие ненужными snapshot-обёртки только после
  подтверждения отсутствия вызовов.
- `setupKeyProcessor()` оставить без изменения поведения.

### Обновление интерфейса

- В `get_web_interface()` заменить имена переведённых `.htm` на `.htm.gz`.
- Тип всех интерфейсных файлов остаётся `SAVE_FILE_OVERRIDE`.
- Версия записывается последней по существующему контракту.

### Документация

- Описать статические gzip-страницы и `/ui-bootstrap`.
- Явно указать единственное исключение: `setup.htm` остаётся шаблонным и несжатым.
- Удалить утверждения, что остальные страницы получают начальные данные через
  плейсхолдеры.
- Обновить codebase-map nodes `data`, `webserver-ino`, `tools`.

## Общая проверка

Порядок обязателен, сборка и smoke-тесты не запускаются одновременно:

1. `python3 tools/build_web_assets.py`.
2. Все целевые static/source-derived тесты с проверенными мутациями.
3. Все целевые браузерные тесты через `playwright-cli`.
4. `python3 tools/run_smoke_tests.py`.
5. `python3 tools/run_browser_tests.py`.
6. Последовательная сборка всех окружений из актуального `platformio.ini`.
7. `python3 tools/check_stepper_isr_iram.py` по собранным ELF.
8. Повторная сборка `data/` и проверка детерминированности.
9. Проверка размера `data/`, ожидаемое уменьшение примерно на 240 КБ.
10. `git diff --check`, полный просмотр diff и `git status --porcelain`.

## Ревью-цикл

После каждой задачи независимый сабагент проверяет только её diff и контракты. После
общей проверки запускается финальное ревью всего изменения. Каждая найденная ошибка или
предупреждение исправляется, целевые и затронутые общие тесты повторяются, затем ревью
запускается снова. Цикл заканчивается только формулировкой: «ошибок и предупреждений
нет».

## Критерии завершения

- плейсхолдеры остались только в `setup.htm`;
- десять целевых HTML находятся в `data/` только как `.gz`;
- все начальные данные целевых страниц приходят через `/ui-bootstrap`;
- ошибка bootstrap всегда видима и не включает fallback;
- `/save`, `/program`, `/ajax` и `setup.htm` сохранили прежнее поведение;
- полные smoke, browser и семь PlatformIO-сборок проходят;
- независимое финальное ревью не содержит ошибок и предупреждений;
- коммит не создаётся без отдельной просьбы владельца.
